# 导航与断言纪律（2026-10-27 真机验证沉淀）

## 底栏 Tab 定位陷阱（最高频失误）

- **不要用裸 `text=首页` 定位底栏 Tab**：「我」页常有"进入首页"入口、详情页有"回首页"按钮，裸文本定位会误命中页面内元素而非底栏。
- 正确做法：底栏 Tab 优先按**屏幕位置约束**（bounds 落在底部区域 y>2000 的可点节点）+ 文本双重确认；或用 resource-id（如 `bottom_nav` 容器下的子项）。
- 真机教训：deepseek 在掘金 S2 用例中 3 次卡在「我→首页」切换，均因定位歧义；glm/qwen 按位置约束绕开。

## 转场纪律

- 点击/跳转后**必须 `wait_idle` 再做任何断言**（lint 规则 assert-after-click 强制）。
- Tab 切换后若 `screen_diff` 树哈希未变，视为切换未生效，重试一次并换定位策略。

## 断言判据

- 断言只描述**当前屏幕可见元素**（lint 规则 inferred-assert / universal-assert 强制）。
- 禁止推断式表述（"已进入XX页"）、全称量词（"所有…都"）、颜色词。
- 主动 terminate/force-stop 期间**不要调 `assert_no_crash`**：进程消失、前台离开 App 都是该窗口的预期状态；用 `processAlive` 或 `foreground` 判断。

## 长列表采样

- `data_extract(mode=collection)` 每屏产量取决于容器粒度：容器选到整列表时字段只取首个匹配 → 每屏 1 条。
- 欠采样时改用：不传容器分条提取、或多轮 ui 模式分屏提取后由主键去重。

## 启动与恢复

- `terminate` 后重启用 `launch(包名)`，恢复后先 `wait_idle` 再操作；冷启动比热切换慢，超时给足。

## 用例粒度：引擎直执行 vs agent 自主（性能关键）

**实测教训（C1 全站巡检）**：把"依次点 6 个分类"写成一个 `ai:` 步骤时，模型会自主规划出
6 组 `tap→wait_idle→screen`，**每次点击都要一轮 LLM 请求**（约 26 秒）——104 轮往返吃掉
总耗时的 **90%**（3002 秒里 2712 秒在等模型）。改造为引擎直执行后降到 **673 秒（−78%）**。

**判据：目标元素能否"预先确定"？**

| 情况 | 写法 | 模型往返 |
|---|---|---|
| 点**已知**按钮（有明确文本/资源 id） | `aiTap: 热榜` | **0** |
| 滚动 / 返回 / 按键 | `aiScroll` / `aiKeyboardPress` | **0** |
| 等画面稳定 | `aiWaitFor`（纯引擎，**不要**写条件文本指望它判定） | **0** |
| 断言（要看画面判断） | `aiAssert` | 1 |
| AI 提取 / 落库 | `aiQuery` + `name:` | 1 |
| **"点开第一条"这类需要先看画面的** | `ai:`（保留，**不要硬拆**） | n |

**反例（慢）**：
```yaml
- ai: 依次点击顶部分类「关注」「推荐」「热榜」「头条精选」「后端」「前端」，每切换一个等列表稳定
```

**正例（快 78%）**：
```yaml
- aiTap: 关注
- aiWaitFor: 列表稳定
- aiTap: 推荐
- aiWaitFor: 列表稳定
# ... 逐个列出
```

**不要过度拆分**：`点开热榜第一条` 这种"需要先看画面才知道点哪"的动作，硬拆成 `aiTap: 第一条`
反而脆弱（模型/引擎都不知道"第一条"指哪个）。**留给 `ai:`**。
