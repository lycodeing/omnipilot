# 步骤上下文逐帧解析（frame-by-frame analysis）

> 对象：run-20261030-010313-fa2a（健康用例，27 步，墙钟 327s）+ 现场实测单帧载荷（emulator-5556，2026-10-30）。
> "帧" = 一步（case step）产生的时间与上下文载荷。

## 一、单帧载荷实测

| 载荷 | 实测大小 | 进上下文形态 |
|---|---|---|
| 截图 PNG（1080×2340） | 418 KB | 压缩为 ~64KB JPEG（540×1200 q70）后随消息发送 |
| UI 树紧凑 JSON（367 节点） | 43 KB | 工具结果文本，全量进当前轮 |
| 单步 prompt 文本 | 50–200 B | user 消息，永久保留 |
| 单步模型回答 | 20–300 B | assistant 消息，永久保留 |

## 二、时间维度逐帧（run3 实测）

| 步类型 | 次数 | 均耗 | 合计 | 占墙钟 | 备注 |
|---|---|---|---|---|---|
| tap_each_row | 1 | 143.9s | 144s | **44%** | 27 tap：每 tap = dump+tap+700ms 等+验证 dump（+hash 未变时截图判蓝） |
| tap（含 VLM 降级） | 10 | 5.3s | 53s | 16% | locate 命中 ~2.2s；VLM 一轮 ~9s |
| aiWaitFor | 4 | 7.9s | 32s | 10% | 含视觉确认轮 |
| scroll | 3 | 9.4s | 28s | 9% | until=selector 小步滚（每次 dump 树检） |
| sleep | 7 | 3.1s | 22s | 7% | 外部框架写法的转场等待 |
| uitree/read | 2 | 1.7s | 3s | 1% | |
| 模型步合计 | — | — | 32s | **10%** | 其余 90% 为引擎/等待 |

**时间结论**：墙钟大头已不在模型轮（10%），而在确定性动作的重复 dump/等待。可省略点：
1. **tap_each_row 的验证 dump**（每 tap 两次树 dump ≈ 3s×27）：hash 未变时才需要像素校验；hash 变了（页面响应）即可记 verified —— 已实现，但"tap 后必等 700ms+一次 dump"仍是下限，可探索"同屏连续 tap（hash 不变即继续）"的自适应批 tap，预计 144s → 60-80s。
2. **sleep 转场帧**：7 步 22s 是给慢 WebView 的保险；已有 aiWaitFor 的场景可逐步替换（保守保留）。
3. **VLM 降级轮**：10 个 tap 中 2 次走了视觉接地（9s/次）——纯描述性目标（"屏幕左上角箭头"）文本定位必 MISS，属预期成本。

## 三、上下文维度逐帧（每步往 session 里放什么）

| 步类型 | 进上下文的内容 | 增长 |
|---|---|---|
| 引擎步（aiTap/aiScroll/aiTapEach/launch…） | **0**（结果不进 session） | 0 |
| ai | prompt + 空轮催答文本 + assistant 文本/工具调用 + 工具结果文本 | 每工具轮已折叠为 ≤300 字符 |
| aiAssert | prompt + 截图 1 张 + 一行 JSON 判定 | 图受 keep-images=3 治理 |
| aiWaitFor | 视觉确认轮（单词判定）×1-3 | 小 |

现有三层剪枝（每步 finally）：
1. `pruneImages(keepRecent: 3)` — 旧截图 → 文字占位
2. `pruneToolResults(keepRecent: 1, keepChars: 300)` — 旧工具结果 → 300 字符摘要
3. `pruneToolHistory(keepRecent: 0)` — 全部工具轮折叠为纯文本（网关 400 根治）

**仍然无限增长的**（本次要治理的"帧"）：
- 所有历史步的 **prompt 文本**（每步 50-200B）
- 所有历史步的 **assistant 回答**（含空轮催答残留）
- 所有历史步折叠后的 **"[工具结果] …300字符" 行**

38 步 run 实测累积 ≈ 25-40KB 文本（≈ 8-12k tokens），叠加 3 张保留图 + system prompt ≈ 单轮 15-20k tokens。步数翻倍则线性翻倍 —— 与"逐帧可省略"结论一致。

## 四、可省略/优化清单（→ 已实现项标注）

| # | 发现 | 处置 |
|---|---|---|
| 1 | 历史步 prompt/回答原文对后续步几乎无用（每步目标独立） | ✅ **步骤上下文窗口**：默认只保留最近 3 步原文 + 确定性整体描述（`src/session/context-window.js`） |
| 2 | 折叠的 300 字符工具残留随步数线性膨胀 | ✅ 随窗口一并移除（窗口外的段整体删除） |
| 3 | 空轮催答文本累积在历史里 | ✅ 归属所属步段，窗口外一并移除 |
| 4 | 引擎步不进上下文（已是 0） | ✅ 保持；引擎步结果以一行形式进"整体描述"。例外：引擎 MISS 的视觉接地降级轮会进 session（1 轮 prompt+回答），按所属步计入该步 delta |
| 5 | 图 keep 3 对断言密集用例仍偏多 | 保留 `--keep-images` 可调（已有） |
| 6 | tap_each_row 每 tap 两次 dump | 后续优化项（自适应批 tap），本次不动 |
| 7 | 前缀稳定性（Manus 教训） | ✅ 窗口折叠只动历史中后段；system prompt 永远首位 |
| 8 | 断言结果不能丢（Manus：keep errors in context） | ✅ 整体描述中显式带"断言 x/y 通过"与最近失败行 |

## 五、整体描述（确定性摘要）格式

```
【整体进展】用例《健康自测-中医体质辨识完整测评流程》共 30 步，已完成 15 步
最近：#12 tap_each_row  ✓；#13 scroll down ✓；#14 tap 立即提交 ✓
断言 3/3 通过
已落库数据集：hotlist=3条（后续数据集断言以此为准）
以下仅保留最近步骤的完整上下文，更早步骤细节已省略。
```
（实际措辞以 `buildStepDigest` 输出为准：含"共 N 步，已完成 X 步"、最近 8 步行、断言计数、
数据集行、变量行；无"无失败步骤"文案，失败以断言失败列表表达。）
